Run the Fixture Builder in SolidWorks

Please use a licensed copy.

For volunteers with SolidWorks 2018 or newer on Windows. You do not need to write code. Windows PowerShell must be available to pack the zip. The builder makes the supported booklet recipes with real SolidWorks features, then saves native files and matching STEP copies. Recipes it cannot make are listed with a reason, not silently left out.

Launcher (recommended)

Install one small macro, once, and from then on your part is "run it". The launcher downloads the current builder, checks it, runs it and (if you agree) uploads the zip.

  1. Download FixtureLauncher.bas. In SolidWorks click Tools > Macro > New, save it as FixtureLauncher.swp, then in the editor choose File > Import File… and pick the .bas. You only do this once.
  2. Click inside main in the FixtureLauncher module and press Run. It does not ask about uploading: when the builder finishes it shows where the zip is, and you post it in the thread as usual. That is the normal route.
  3. It downloads latest.json and the builder into %LOCALAPPDATA%\DutchmanFixtures\, compares the SHA-256, and only runs a builder whose checksum matches. If the checksum does not match it stops and keeps the previous good copy. Offline, it uses the last verified copy and says so. If the server has no latest.json yet it still downloads the builder and logs "no manifest, checksum not verified".
  4. It imports the builder into the open VBA project and runs FixtureBuilder.main. If SolidWorks refuses access to the VBA project (some setups need "Trust access to the VBA project object model" turned on) it tells you the exact file to import by hand (File > Import File…) and to run FixtureBuilder.main.
  5. When the builder finishes, the launcher shows the zip path. Posting that zip in the thread by hand is the normal route. Automatic upload exists but is off unless you turn it on in settings: it asks whether to upload after each run and, if you say yes, for your private portal link (like https://fixtures.dutchmancad.xyz/v/...), which stays on this computer. With it on, the launcher sends the zip with curl.exe (part of Windows 10 and later) to your link plus /builder and shows the receipt.

Other macros in the same module: settings (change run mode and output folder, turn automatic upload on, or turn it off again, which also clears the stored link) and upload (send the last zip again; it works only when you have turned upload on in settings, otherwise it explains how). Your answers are kept in the Windows registry under DutchmanFixtures / SolidWorksBuilder; OutputRoot replaces the builder's default output folder, but only a neutral one: settings refuses a folder inside your user profile, a folder named after your Windows user name, a OneDrive folder, or any other Users\<name> folder, and says why (SolidWorks keeps the full path of the files it references inside every assembly and drawing it saves, so such a folder would put your user name, and a company OneDrive's name, in the files you send). Leave it empty to use C:\Users\Public\Documents\FixtureBuilder.

Everything the launcher does is written to %LOCALAPPDATA%\DutchmanFixtures\launcher.log (times, versions, which route worked, results). Your private link is never written whole: only its last four characters appear.

Download and run (manual, without the launcher)

Save and close your own work first. Start SolidWorks with the default metric templates available. Allow roughly 10–30 minutes for a batch; older machines and large sets may take longer. This is an estimate, not a measured promise. Leave SolidWorks alone while it runs.

One macro serves every SolidWorks version: it uses the same calls and the same fallbacks on each one. Volunteer runs so far are on SolidWorks 2021, 2023 and 2026. Only the several-edge flanges need SolidWorks 2022 or newer; on older versions they report that and the rest of the batch continues.

  1. Download FixtureBuilder.bas.
  2. In SolidWorks, click Tools > Macro > New. Save the new macro as FixtureBuilder.swp anywhere you like. The Visual Basic editor opens.
  3. In that editor, click File > Import File… (File > Import), and select the downloaded .bas file. Use the imported builder module, not the empty starter macro.
  4. The macro writes into C:\Users\Public\Documents\FixtureBuilder (it makes that folder if needed; if Windows has no Public folder it uses C:\FixtureBuilder). That folder is on purpose: a SolidWorks assembly or drawing keeps the full path of every file it references inside itself, so a folder in your profile (C:\Users\<you>\Documents) or in OneDrive would put your Windows user name, and a company OneDrive's name, into every assembly and drawing in the zip. Public holds no user name and OneDrive does not sync it. To use another folder, set OUTPUT_FOLDER near the top of the module; the macro refuses a folder inside your user profile, one named after your Windows user name, one with OneDrive in its path, or any Users\<name> folder other than Public, shows why, and builds nothing. The first lines of FixtureBuilder.log say personal-path check: passed. A run that you made earlier in Documents\FixtureBuilder is not seen from the new folder, so the first run there builds everything again. Inside it the macro makes its own new folder, FixtureBuilder-SolidWorks-<version>; if that name is already taken (a run from earlier), it uses -2, then -3, and so on. It never deletes, empties or reuses a folder, so you do not need to prepare one. Click inside the imported module's main procedure, then Run > Run Sub/UserForm. The macro runs without an output-folder prompt. If asked which macro to run, choose FixtureBuilder.main.

If your templates live elsewhere, set TEMPLATE_PART to the full .prtdot path at the top of the imported macro (or Python script).

Downloads come from fixtures.dutchmancad.xyz/builders/. Use the SolidWorks guide and builder files there. Keep the downloaded .bas separate from the .swp you create.

What happens on your machine

The builder makes a new output folder named FixtureBuilder-SolidWorks-<version> (-2, -3 ... when that name is taken), opens documents to make the fixtures, saves them, and closes the documents it created. It never changes, deletes or overwrites your existing files or an earlier run's folder. It writes native files, .step copies, results.json, and one zip named after the folder; the first line of FixtureBuilder.log gives the full folder path and the SolidWorks revision. Keep assembly parts with their assemblies.

Open results.json in a text editor when it finishes. ok means that recipe was saved; failed includes the app's error; not_scripted explains what still needs making by hand or a newer app. Partial batches help too. A saved file still needs the portal's checks.

Assemblies A11 to A26 (placements, nesting, motions, mirror, patterns, links, flexible, configurations)

The builder makes all of these assemblies for you: A11 (the same part twice, with turns), A12 and A13 (an assembly inside an assembly, two and three levels), A14 to A19 (a rigid joint, a turning motion with limits, a slide with limits, a slide and a turn, a motion on a plane, a turn about a point), A20 (a mirrored component), A21 and A22 (a linear and a circular pattern of a whole subassembly), A23 (linked parts, Make Virtual, editing the source part), A24 (a flexible subassembly), A25 (suppressed parts, and a suppressed mate) and A26 (a part configuration). SolidWorks has no slider, cylindrical, planar or ball mate, so each motion is made from Coincident, Distance and Angle mates, and the travel limits are the Max and Min values of the Distance and Angle mates. Each part you place is the part's own file from the same run folder.

Where an assembly sits inside another (A12, A13, A21, A22, A24), the builder first makes the inner one in its own file, named as the booklet names it (A12-sub.sldasm, A13-pair.sldasm, A13-mid.sldasm, A21-pair.sldasm, A24-pair.sldasm), saves it in the same folder as the top assembly, and then places it. Those extra files go into the zip too; leave them next to the top file when you open it.

Some recipes change a part. The builder never changes P01a.sldprt or any other part file of the run, because other recipes use it: A23c works on a copy named A23c-P01a.sldprt (it makes the copy, edits it to 12 high, rebuilds the assembly and checks that the block is 12 high), and A26a and A26b each use a copy with two configurations (A26a-P01a.sldprt, A26b-P01a.sldprt: Default 10 high, Tall 12 high), with the pin mated to the block's top face. A20c saves the new mirrored part as P04a-mirrored.sldprt beside the top file. These copies go into the zip as well.

What the builder does for the new kinds, in SolidWorks words: A20 Mirror Components about a reference plane at the recipe's offset (an instance of the same file for a and b, a new part file for c; the log says which component orientation put the rounded corner on the mirror image, and the builder tries the four orientations in turn until one does); A21 and A22 Linear Component Pattern and Circular Component Pattern with the subassembly picked as one component (the log lists the instances it found); A23a places both parts from their own files (a file link) and checks they are links, A23b Make Virtual on the pin, A23c the edit and the update; A24 Solve as Flexible on the instance, then the pin dragged by 6 mm inside that instance; A26 Configure Component with Tall active.

After each of these assemblies the builder reads the position and turn of every part back from SolidWorks and compares them with the answer key. The result is one line in FixtureBuilder.log (step placement check) and a placements entry in results.json: pass or fail, and for a fail which part is where. It also checks what the answer key says besides position: which configuration a part references (A26), whether a part is a link or a virtual copy (A23), whether a subassembly instance is flexible (A24), which file the mirrored part is (A20c) and, for the mirror (where position and turn are not compared), the overall box. A fail does not stop the file being saved, so you still get it (it is in the zip), but the recipe is then reported as failed with the text placement check: fail (N of M): ... as its error, never as ok, and the line tells us whether the placement or the way the builder asked for it was wrong. The same goes while the mates are made: after each mate (after the last one, for a part that was placed away from its pose) the builder reads the part's position and turn, and a part that is off its pose is undone and mated once more with the other Flip or alignment (mate-flip-retry); wrong again, the recipe fails and says where the part ended up. A component pattern whose instances are mirrored or swapped is undone and made once more with the direction reversed (pattern-direction-reversed). The mirrored part of A20c is checked against its own geometry (the axis of its rounded corner), like an instance. The edited part of A23c and the configured copy of A26 are saved by the builder and read back from the saved file. The limit mates are the least proven part: if SolidWorks refuses a limit, the builder makes NO mate for that motion (a plain distance or angle mate would lock it): the motion is left free at the saved pose, the row says "limits ... not stored" (limits and degraded in results.json) and the card should say "no limit". Where a limit mate is made, its limits are read back (IMate2.MinimumVariation / MaximumVariation) and put on the row, or the row says "limits not read back". In the same way the log names every other step where the first way did not work and another was used (for example mirror-orientation-next, pattern-feature-data, flexible-move-transform2, make-virtual-selected, config-dimension-this-configuration); the line mitigations: of each recipe counts them.

If SolidWorks refuses a step that has no other way, the recipe shows failed with the step and what was tried; send the zip and the log as usual. Nothing in A11 to A26 needs to be made by hand any more.

New log lines in 2026.11.24.4

The first real run showed six things; the builder now says what it did about each in FixtureBuilder.log (steps zip and option):

  • zip: lines and <folder>-zip-error.txt. The builder now checks that the zip exists. If it does not, it closes every document and tries again (zip-verify-retry, the error text goes to FixtureBuilder-SolidWorks-<version>-zip-error.txt beside the folder), then writes the zip a second way (zip-shell-application). An old zip of the same name is deleted first, and a zip counts only if it is complete. The zip steps log their own mitigations: line. If both fail the finish message tells you to right-click the folder, choose Send to > Compressed (zipped) folder and send that.
  • limits ... stored (read back relative to the pose ...). SolidWorks reports a limit relative to the mate's own value; the builder adds the value back, so a limit is degraded only when it really differs. limit-mate-negative-flip means a negative distance was made as its size with Flip toggled (SolidWorks refuses a negative value).
  • MirrorComponents3 form N (...) returned .... One line for each way the mirror was asked: what came back (nothing, an empty array, an object), whether a new component appeared, and the last feature in the tree. A form that answers an empty array is not a success; the next form is tried (mirror-empty-array-nothing, mirror-empty-variant, mirror-plane-selected, mirror-refplane-object).
  • move ... Transform2 (...), GetTotalTransform (...), box center (...). After each way of dragging the pin the builder logs three readings of where it is; the box center decides whether it moved (flexible-move-world-transform first, then flexible-move-transform2). For a part that was dragged, the final placement check compares GetTotalTransform with where the box says it is (its position before the move plus how far its box moved); if they differ the line GetTotalTransform misreports a flexible child; X/Y judged by the box center says so (placement-flexible-box). Other parts are judged by GetTotalTransform as before.
  • configuration X depth: geometry ..., GetSystemValue3 ..., SystemValue .... The depth of each configuration is read from the part's geometry; the two dimension readings are logged beside it and marked when they disagree. SetSystemValue3(...) returned N gives SolidWorks' answer to each write; config-dimension-this-configuration and config-dimension-fresh-handle are the other ways of writing it.
  • base flange attempt failed (SolidWorks 2021 sheet metal). On SolidWorks 2021 every sheet-metal recipe failed because InsertSheetMetalBaseFlange2 made nothing and IBaseFlangeFeatureData has no Initialize (Err 438), and the log did not say why. Now every failed way of making the base flange is logged as it happens, with its inputs, what is selected and the profile sketch (feature type, name, segment count). The ways are: the corrected call; the API Help example's call (baseflange-doc-example); the feature-data route (baseflange-featuredata), which sets the members directly when Initialize raises and puts the K-factor on the Sheet-Metal feature afterwards (baseflange-featuredata-no-initialize, default relief); and the corrected call again with the profile sketch selected by name with SelectByID2 (baseflange-selectbyid). The older InsertSheetMetalBaseFlange is not tried (its arguments are not documented). If all four fail, the recipe's error carries every reason.

New log lines in 2026.11.25.2

A SolidWorks 2026 run of 2026.11.25.1 made 143 recipes and failed five (A20a, b, c, A24a, b). What the builder says and does about each now:

  • A20 (the mirror plane). The mirror made nothing ("returned an array (UBound -1, 0 object(s)); no new component; last feature MateGroup"): the plane was taken as the newest feature after the offset plane was made, and in an assembly that is the Mates folder, because a new reference plane goes above it. The builder now takes the newest reference plane (reference plane N mm from YZ: RefPlane... (RefPlane) in the log).
  • drag handle of ...: selected as ... (A24). On 2026 the drag operator answered False from AddComponent for the pin found through the top assembly's component tree and moved nothing. The builder now selects the pin by its full component path and gives the operator the component the selection manager answers for it (the pin as the top assembly sees it). If that selection gives nothing the line lists every form tried, and the handle used before is the fallback; the move ... line shows AddComponent returned False (selected handle) and ... (current handle) when both were asked.
  • move ... temporary Concentric mate to the axis (...) (A24, flexible-move-temporary-mate). On 2026 SetTransformAndSolve2 (with the world and with the local transform) and a Transform2 put answered True and put the pin at the pose it has inside its own subassembly, (0,0,10), for every handle. So right after the drag operator fails the builder makes a temporary reference axis (a 3D sketch line, then Insert Axis) through the place the pin must go, a Concentric mate between the pin's cylindrical face and that axis, and reads where the pin is. Then it deletes the mate, the axis and the sketch, rebuilds, and reads the pin again (... deleted and the assembly rebuilt): it must still be at the place, and the assembly must have the mates it had. If the pin goes back when the mate is deleted, or something is left over, the recipe fails and the error gives both readings. The transform rungs only run if this one does not move the pin (in the field SetTransformAndSolve2 never moved the pin on SolidWorks 2021, 2023 or 2026, and on 2026 it reset it, which is why this rung is before it). Before and after the rung the builder compares the mates and the features of the assembly: if a mate, axis or 3D sketch it made is still there, the recipe stops with what is left, so a stray one is never saved and no later rung runs on it. The axis must be a new one, and a 3D sketch left open by an error is closed first.

SolidWorks 2021: the sheet-metal base flange and its K-factor

On SolidWorks 2021 (revision 29) every sheet-metal recipe stopped at the base flange's K-factor. The Help explains the 438 errors: IBaseFlangeFeatureData.Initialize exists from SolidWorks 2022 (revision 30), and SetCustomBendAllowance is not a member of the base flange data at all. What the builder does on a revision before 30 now, and what it logs:

  • The base flange is inserted in the form the Help example uses (baseflange-insert-verified-form, with a K-factor allowance; baseflange-insert-verified-form-no-allowance; then the older 16-argument InsertSheetMetalBaseFlange, baseflange-insert-v1). The earlier two forms had the opposite relief, merge and body-selection flags. A base flange that fails on these revisions reports seven ways.
  • The K-factor is put on the base flange the way releases before 2022 do it: OverrideKFactor and KFactor on the base flange data (inside baseflange-kfactor-on-data), and, after the existing steps, on the built flange (baseflange-kfactor-members-modify).
  • Sheet-Metal feature state: UseGaugeTable=... GaugeTableFile=... UseMaterialSheetMetalParameters=... BendRadius=... Thickness=... (k-factor). A gauge table or the material's sheet-metal parameters in force would keep a K-factor of 0.5. When the earlier steps leave it at 0.5 the state is logged, and sheetmetal-kfactor-gauge-off switches both off and sets the K-factor in one ModifyDefinition.
  • kfactor-continue-diagnostic. If no step takes, the recipe is built to its end instead of stopping, so one run also shows the next problem (edge flanges, hems). The part is NOT saved and the row stays failed; its error starts with the K-factor failure and ends with what the later features did (the later features then built without error; nothing was saved, or the step that failed).
  • A base flange made by the insert call that comes out on the wrong side is now flipped with ModifyDefinition (baseflange-modify-reverse) instead of being refused.

Plates with a hole: F04a and D06a

The builder makes F04a (the 20 x 30 x 10 block of F01a with a simple hole of 5 mm through, at the center of the top face) and D06a (a plate on XY with the sloped corner, profile (0, 0), (60, 0), (60, 20), (40, 40), (0, 40) and back, extruded 10 up, with a simple hole of 10 mm through at (20, 20)). Both use the same steps as the other holes (D04a): the sketch with its dimensions, the extrude, then the Hole Wizard on the top face: a simple hole, through all, placed at the recipe's point. F04a is the part P01a makes plus the hole; the builder does not need a separate F01a file for it. The check after each is the volume and the box from the answer key: F04a 5803.65 mm3 in x -10 to 10, y -15 to 15, z 0 to 10; D06a 21214.6 mm3 in x 0 to 60, y 0 to 40, z 0 to 10. If either differs the row says which number and what was read.

By hand, the same two parts: draw the sketch, extrude 10, then use the Hole Wizard (not an extruded cut): type Hole, end condition Through All, and place its point on the top face at (0, 0) for F04a or (20, 20) for D06a.

Making S04d and S04e by hand

The builder can't script these two hems, because the SolidWorks API has no way to create a Teardrop or Rolled hem with its default values. Each takes about 5 minutes by hand in SolidWorks. You start from the S02a part the builder already made, so you don't draw anything new. (S02i and S04c are skipped in SolidWorks; no file is needed for them.)

  1. Find S02a.SLDPRT from your last builder run. It is in C:\Users\Public\Documents\FixtureBuilder\FixtureBuilder-SolidWorks-<version>\ (or Documents\FixtureBuilder\... if you built with an older version), or inside the zip the builder made (unzip it first).
  2. Open S02a.SLDPRT in SolidWorks. You see a flat plate 100 × 60 with one wall 20 high standing up along its long top edge.
  3. Straight away, choose File → Save As, type the name S04d (type: Part, .SLDPRT), and save it in the same folder. From now on you are editing S04d, and S02a stays as it was.
  4. Choose Insert → Sheet Metal → Hem. Alternatively, on the Sheet Metal tab, click Hem.
  5. Click the free top edge of the wall: the 100 mm long edge at the very top of the upright wall, furthest from the plate. It turns blue and appears in the Edges box.
  6. Under Type and Size, click Tear Drop. Leave every number as SolidWorks shows it.
  7. Look at the yellow preview. The hem must curl back over the plate (toward the inside of the part), not away from it. If it curls outward, click the Reverse Direction button next to the Edges box.
  8. Click the green ✓. A Hem1 feature appears at the bottom of the FeatureManager tree.
  9. Press Ctrl+S to save S04d.SLDPRT.
  10. For S04e, repeat steps 2–9 from S02a again, but name it S04e in step 3 and click Rolled in step 6.
  11. Put S04d.SLDPRT and S04e.SLDPRT in one zip, and send it to Dutchy in a Discord direct message (or post it in your builder thread). Say which SolidWorks version you used, and that these two were made by hand. If you changed any value or clicked Reverse Direction, say so too.

Drawings package (optional)

A second macro for volunteers who have already run the builder: FixtureDrawings.bas draws the parts that run made, using the same drawing code the builder's D05a uses (every call and fallback of D05a is kept), with more of what the booklet's drawing recipes ask for: the base view at its scale, the views projected from it, an isometric view at a scale of its own, a section view with its label, the sheet size, drawing standard and units, the title block text, and linear dimensions. It makes the companion drawing recipes D10a to D19a (D10 F04a, D11 D04a, D12 D06a, D13 P03a, D14 P03b, D15 P07a, D16 P08a, D17 P06a, D18 P06b, D19 F10a), and the main builder never tries them: it lists them as not scripted, "made by the drawings package (FixtureDrawings.bas)". The macro draws these nine (D19a, the parts list, is not scripted), each on an A4 landscape ISO sheet with a Front base view at 1:1, the Right view to its right, the Top view above it (in a first-angle template SolidWorks puts it below; the macro checks which side the viewer is on and moves it, see drawing-projection-opposite-side), an isometric view at 1:2, section A-A through the part, and the title block text "<part> drawing" by "Fixture Builder":

  • D10a, a drawing of F04a (the 20 x 30 x 10 block with a 5 mm through hole at its center, the same shape as P03a): section A-A at x = 0 through the hole, and 20, 30, 10 and the hole's two distances 10 and 15.
  • D11a, a drawing of D04a (the L-shaped bracket): section A-A through the hole's center at x = 25 mm, and D05a's four dimensions 40, 30, 5 and 25.
  • D12a, a drawing of D06a (the plate with the sloped corner and a 10 mm hole at (20, 20)): section A-A through the hole's center at x = 20, and 60 (length), 40 (width), 10 (thickness), 20 (the hole's distance from the left face) and 20 (the straight right edge along Y).
  • D13a, a drawing of P03a (the block with a plain hole): section at x = 0, and 20, 30, 10 and the hole's two distances 10 and 15.
  • D14a, a drawing of P03b (the same block with a counterbored hole): the same section and five dimensions.
  • D15a, a drawing of P07a (the plate with six holes): section at x = 5 through the first column of holes, and 60, 40, 5, the first hole's 5 from the left face, and the hole pitches 10 along x and 10 along y.
  • D16a, a drawing of P08a (the disc with six holes): section at x = 20 through a hole, and 60 (the disc's diameter), 5 (thickness), 20 (hole circle radius, from the disc's center to a hole's center) and 40 (between two opposite holes).
  • D17a and D18a, drawings of P06a and P06b (the open box with 1.5 mm and 2 mm walls): section at x = 0 through the pocket, and 20, 30, 10 and the wall thickness twice.

Each dimension is made from the part's model edges in the view where they show it, never from a silhouette: an edge to the next edge or to a hole's center, or two holes' centers; a disc's diameter is its outline circle in the Top view, selected on its own; its thickness is its two rims in the Front view, where they show as two parallel lines (see drawing-dimension-circle-diameter and drawing-dimension-edge-on-circles below). The recipe's Front is the view with X to the right and Z up. SolidWorks keeps the recipe's XYZ, so that is SolidWorks' Bottom view (its Top view would show +Z pointing down and the L upside down), and the recipe's Top is SolidWorks' Front view; after making the base view the macro checks that model +X really points right and +Z (or +Y for a Top base) really points up on the sheet, and fails with the numbers if not. The recipe's Right, Back, Bottom and Left have no SolidWorks standard view with Z up, so as a base view they say not_scripted, "needs a rotated view". A recipe whose model is not a SolidWorks builder recipe (D10a F04a, D12a D06a, D19a F10a, which also needs a parts list) is not in the SolidWorks spec, so the macro does not list it.

  1. Run the Fixture Builder first (the launcher or the manual way above), and keep the folder it made, FixtureBuilder-SolidWorks-<version>: the macro draws the parts that are in it (D04a.sldprt and so on).
  2. Download FixtureDrawings.bas.
  3. In SolidWorks, click Tools > Macro > New. Save the new macro as FixtureDrawings.swp anywhere you like. In the editor that opens, click File > Import File… and select the downloaded .bas. Use the imported FixtureDrawings module, not the empty starter macro. This is the same as importing the builder.
  4. Click inside the imported module's main procedure, then Run > Run Sub/UserForm. If asked which macro to run, choose FixtureDrawings.main.
  5. A box asks for the folder of the earlier builder run. It already holds the newest FixtureBuilder-SolidWorks-* folder under your builder output folder (C:\Users\Public\Documents\FixtureBuilder, or the neutral folder you chose in the launcher's settings; the old Documents\FixtureBuilder is not looked in). Press OK, or replace it with the folder of another run. Cancel (or an empty box) does nothing at all. The run must come from the Fixture Builder 2026.11.25.3 or later: a run made in a personal folder is refused ("This run was made in a personal folder, so its parts carry that folder's path. Run the Fixture Builder 2026.11.25.3 or later first; it saves to C:\Users\Public\Documents\FixtureBuilder.") and nothing is drawn, because each part keeps its own save path and each drawing keeps the part's. Like the builder, the package shows the user name notice once (OK or Cancel) and checks your drawing template for a personal path.
  6. Wait, and leave SolidWorks alone: for each part the macro opens the part, makes a new drawing from your default drawing template, builds the views and dimensions, saves the drawing, a PDF and a DXF, and closes both. Allow about a minute for each drawing; that is an estimate, not a measured promise.
  7. When it finishes it shows how many drawings were made, failed, not scripted or skipped, and the path of the zip. Post that zip in your builder thread as usual (or send it to Dutchy in a Discord direct message).

What it makes: a new folder FixtureDrawings-SolidWorks-<version> (-2, -3 ... when that name is taken) in the same neutral output folder as the builder (C:\Users\Public\Documents\FixtureBuilder, not beside a run in a personal folder; it is made if missing), with, for each drawing, <recipe>.slddrw, <recipe>.pdf and <recipe>.dxf (for D11a: D11a.slddrw, D11a.pdf, D11a.dxf; DXF version R2000, like D05a's; D13a to D18a the same), plus FixtureDrawings.log, results.json and one zip named after the folder. Each results.json row has the usual shape: id (the recipe, for example D11a), status, error, files, app, version, build, mitigations and seconds. ok means the drawing was saved and read back; failed gives the step and the call inputs, and the next part carries on; not_scripted says why the drawing is not scripted (the model is not a SolidWorks builder recipe; or detail views, parts lists, several sheets, a dimension with no points to measure between are not scripted yet): it never makes a drawing with less in it; skipped means "the part file is not in this folder" (the part the drawing is of, for D11a D04a.sldprt, for D13a P03a.sldprt, and so on).

It never changes the run folder. The parts are opened read-only and silently, and closed without saving; nothing is written, renamed, deleted or locked in that folder. FixtureDrawings.log and results.json name folders and files, not paths. A drawing, like every SolidWorks drawing (the builder's D05a included), keeps SolidWorks' reference to the part file it shows, and that reference includes the part's path on your computer. So the files are private by default like the builder's, and the portal's own privacy scan and the CC0 choice at upload apply to them as they do to the builder's files. Before saving, the macro blanks Author, Company, DrawnBy, CheckedBy and the summary fields, as the builder does (Author and Saved By get the neutral name Fixture Builder, Keywords and Comment are blank, and the log reads them back after each save); a fixed, non-personal title block text from the recipe is set after that, so it stays. Every message and log line is scrubbed, and the whole output folder is swept before the zip and on every way out of a run, exactly as in "Privacy and sending the zip". The package makes no STEP file, so the STEP header check does not apply.

What it reads back from SolidWorks, and fails on precisely: the sheet's size, standard, units and scale; the axis every view looks along (the base view, each projected view, the isometric view must not be axis-aligned, the section view must look along the cut plane's normal); the section view's label; every dimension's measured value and the full list of dimensions in the drawing; the title block text as drawing custom properties; and that the PDF and the DXF hold data.

The mitigation names in results.json and FixtureDrawings.log (each counts how often the first way failed and the second worked):

  • drawing-projection-opposite-side: a projected view came out looking along the wrong axis (the template's projection sends it the other way), so the macro deleted it, placed it on the opposite side of the base view and checked again; still wrong on both sides is a failure.
  • drawing-view-scale-explicit: a view was not at the sheet's scale, so the macro set that view's scale itself and read it back. (The isometric view's own 1:2 is not a mitigation: it is always set on that view and read back.)
  • drawing-select-entity-via-view: Select4 could not select an edge of a view for a dimension, so the view's own SelectEntity did.
  • drawing-section-line-reselect: the section line was not left selected after it was drawn, so the macro selected it again.
  • drawing-sheet-size-set, drawing-standard-set, drawing-units-set: your template's sheet size, drawing standard or units differed from the recipe's (A4 landscape, ISO, millimeters), so the macro set them and read them back; a setting that does not stay is a failure.
  • drawing-dimension-circle-diameter: D05a's own way of choosing the edges (a line, or two references) found nothing for a dimension, so the macro selected one circle seen face-on on its own, which gives a diameter dimension (IModelDoc2.AddDimension2): the disc's 60 in D16a. A circle's axis (ICurve.CircleParams) that is zero or not a unit vector is unknown and the form is not used.
  • drawing-dimension-edge-on-circles: the same, with two circle edges one of which is seen edge-on, where it shows as a straight line (the disc's two rims in the Front view: its thickness 5 in D16a). SolidWorks dimensions two circle edges between their centers, which is the distance between the lines. The log then holds a line "edge-on circles: ..." with each circle's CircleParams as SolidWorks reported them, the number of edges selected and the type of the dimension it made. If the value does not read back, the failure says "edge-on circles: SolidWorks measured <value> mm, not center to center".
  • drawing-section-outline-fit: the base view's transform did not put the model inside the view's outline (it is not in sheet meters), so the macro placed the section line from the outline instead: the transform's rotation, the view's own scale, and the model box centered on the outline's center. The log gives the numbers, and also the section line's end points as SolidWorks reports them beside the ones asked for.
  • drawing-sheet-scale-from-views: SolidWorks would not report the sheet's scale, so every view's own scale was checked instead.
  • title-block-property-only: the title block text was set as drawing custom properties and read back, but your template's title block notes do not show it (no title block, or one that does not link those properties). The macro logs this and never says the text is on the sheet.
  • zip-verify-retry, zip-shell-application: the same zip fallbacks as the builder.

Privacy and sending the zip

SolidWorks writes your Windows user name into each file it saves. We keep these native files private and publish only STEP and files we've checked clean; to keep your name out of the files entirely, run SolidWorks under a neutral Windows account. The builder says this before it builds anything (one OK/Cancel box, once per run; Cancel builds nothing) and the log records that it was shown and the answer. SolidWorks stamps the saving user in the file's summary information (and in a header field) at every save, and the SolidWorks API gives a macro no way to switch that off or to write the saved-by field (see builders/solidworks-api-audit.md), so every run logs SolidWorks stamps the saving user in each file: not removable by the API.

SolidWorks also records its Windows temp folder (under your user profile) in each native file; we keep native files private and publish only STEP and files we've checked clean. A macro cannot change that folder (it is the SolidWorks process's own TEMP), and the builder does not touch your SolidWorks options, so it only says so: every run logs the same sentence. To avoid it entirely, run SolidWorks under a neutral Windows account.

What the builder does control: before each save it sets the summary fields it may set, Author (and Saved By where SolidWorks lets a macro write it) to the neutral name Fixture Builder and Keywords and Comment to blank, and the Author, Company, DrawnBy and CheckedBy custom properties to blank. After each save it reads the summary fields back and the log gives one line, summary info read-back after save: author=... keywords=... comment=... savedby=..., where each is Fixture Builder, blank or set by SolidWorks (redacted); a value that is not ours is never logged. The output folder and the document templates are checked for a personal path before anything is built (see step 4 above): a drawing stores the path of its template, so the log says template path: neutral or the run is refused with a message that does not repeat the path. Every file in the output folder (not only the listed ones) is swept before the zip: text files (.log, .json, .txt, .csv) have your profile folder, the folder after Users\ (except Public) and your Windows user name replaced by <user>; a file that cannot be read or written is truncated, then removed, and the log says so; lock files (~$*) and temporary files are deleted. The sweep reads each file as UTF-8, UTF-16 (with its byte-order mark) or the ANSI codepage the log is written in, matches your name as Unicode (so a Cyrillic or CJK user name is found too) and writes the file back in its own encoding; a file it cannot decode with certainty, one over 4 MB, or one with stray NUL bytes counts as a hit and is truncated or removed, never passed as clean. Any stray file in the output folder is dealt with too, whatever its extension: text-like files (.log .json .txt .csv .tsv .xml .html .htm .md .ini .cfg .yaml .yml) are scrubbed, .tmp and lock files are deleted, and any other file the builder did not make is searched byte for byte for your name and the computer, domain and logon-server names in UTF-8, UTF-16 and the ANSI codepage and deleted on a hit, on a size over 4 MB or on a read error. After every STEP export the builder reads the first 4 KB and requires FILE_NAME to be a bare file name with an empty (or Fixture Builder) author and organization; otherwise it rewrites those fields and logs step header: rewritten, or fails the row if it cannot. Under Users\\<name> (only Public, Default, All Users and Shared, spelled exactly, are exempt: Public.x is not) everything after the name up to a quote, a line end or one of < > | is replaced (C:\\Users\\<user>\\<path>, so a Dropbox (Company) folder leaves nothing), a name with a space is replaced as a whole, a name of 3 or more characters (not a common word such as admin, user, test, work, office or desktop) is replaced wherever no ASCII letter or digit is next to it (the start of a file, after a tab, inside quotes, after a length byte; a Cyrillic or Greek name in any case) while a one or two character name only as a whole folder name, and the profile folder's own name (often not your user name), the OneDrive folders, the redirected Documents folder, the computer, domain and logon-server names and any \\\\server\\share prefix are replaced too. The output folder is refused on a network share or when it is under your profile, a OneDrive folder or the redirected Documents folder, or has the computer, domain or logon-server name as a folder name. The default folder C:\Users\Public\Documents\FixtureBuilder is checked by the Users\<name> and network share rules only, so a user called Documents or Public is not locked out of it. Every value is scrubbed before it is written as JSON, so results.json stays valid, and a path in an error text is replaced to the end of its line (a folder name with spaces leaves nothing behind). Right after SolidWorks writes a DXF it is scrubbed as text; a PDF is searched for the names and, if one is in it, deleted and the recipe fails with privacy: pdf carried a personal name (the compressed .sld* files are not searched). If a text file had to be emptied or deleted because it could not be cleaned, the finish message says N file(s) could not be cleaned and were emptied: <names>, because the zip is then incomplete. An output folder (or, for the drawings package, a run folder) must be a full path that starts with a drive letter: FixtureOut, ..\x or %USERPROFILE%\x would be read against SolidWorks' own current folder, which can be under your profile, so they are refused with "the folder must be a full path starting with a drive letter". If the sweep cannot list a folder (access denied, a path too long) it says privacy sweep: could not list <folder>, no zip is made, and the finish message says "the zip was not made because the output folder could not be checked; nothing was sent". A file over 4 MB is reported as "too large to check (over 4 MB)", not as carrying a name; a name with characters the ANSI codepage cannot hold is still searched in UTF-8 and UTF-16 and the log says ansi form not applicable. A //server/share path is replaced like \\server\share. An error after the sweep (in the zip step) triggers a second sweep on the way out. The sweep runs on every way out of a run, including an error part way, so a crash leaves no unswept text file. Every message box and error text goes through the same replacement. Template lookup errors include every path tried so you can fix the template configuration, with any personal part replaced by <user>. Other errors omit personal paths. The portal's own privacy scan still runs; blank properties do not replace that scan. Files stay private unless you choose CC0 when uploading.

Native CAD files (.sldprt, .sldasm, .slddrw…) carry your Windows user and computer name inside them; we keep native files private and publish only STEP and files we've checked clean.

Open your private contributor page on the portal, go to its bulk upload page, and choose the generated zip. Say “SolidWorks Fixture Builder” and give your SolidWorks version and build in the note. Read the receipt and any rejected-file reasons. If the page cannot accept your batch, use the link option below.

If you turned automatic upload on in the launcher's settings (it is off by default), it sends the same zip straight to your private contributor page (your link stays on your machine) and shows the receipt: how many recipes were built, failed, not scripted, or skipped because they already built on this version. Sending the same run twice records it once. Files stay private unless you choose CC0.

Alternatively, upload the zip to Google Drive or Dropbox and send the sharing link to Dutchy in a DM, with the same version and builder note. Keep your portal link private. Do not describe a scripted batch as made by hand or agree to a statement that does not describe your run.

The macro uses the standard SOLIDWORKS type library reference supplied by a normal SolidWorks VBA macro project for explicit PartDoc, AssemblyDoc and Entity interface conversions.
