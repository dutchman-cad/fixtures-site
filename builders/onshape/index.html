Onshape Fixture Builder

Generated script: build_onshape.py.

The generated Python 3 script builds the recipes as native Onshape Part Studio features (sketches, extrude, revolve, hole, fillet, chamfer, shell, loft, sweep, patterns, mirror, split, helix, variables, sheet metal) through the Onshape REST API, with your own API keys. The source is builders/gen/emit_onshape.py and builders/gen/onshape_runtime.py; regenerate with python3 builders/gen/generate.py. Do not edit the distribution script.

`sh export ONSHAPEACCESSKEY=... # Onshape: My account, Developer, API keys export ONSHAPESECRETKEY=... python3 build_onshape.py --only P01a P04a --max-calls 40 `

The output folder is the optional first argument. It defaults to a folder outside every user profile: C:\Users\Public\FixtureOut on Windows, /Users/Shared/FixtureOut on macOS and /var/tmp/FixtureOut elsewhere.

Each run creates ONE new Onshape document with isPublic: false and one Part Studio per design. It stops before adding any feature if Onshape reports the new document as public; on a plan whose documents are always public, nothing is built. It never edits or deletes an existing document.

Privacy. No user profile path reaches a kept file or a file you send.

  • The builder refuses an output folder whose resolved path is inside your home folder, has your user name (or the last folder name of your home folder) as a folder name, or contains OneDrive in any letter case. It prints which rule applies and the default folder, never your user name, and exits before any API call.
  • After each kept file is written (<id>.onshape-bundle, <id>.step, <id>.pdf, <id>.dxf, <id>.drawing.json) it scans the file: the raw bytes, every zlib and raw-deflate stream inside it, and every ZIP member, in ASCII and UTF-16LE. It looks for your home folder, your user name as a folder name, a Windows user-folder path (under X:\Users), a home-folder path under /home or /Users (/Users/Shared/ is allowed), OneDrive and a network-share path. A file with a hit is deleted and its design fails with privacy: <file kind> holds a user path (<pattern kinds>); the message names the kinds and never the matched text. The scan is bounded (64 MiB per stream or member, 256 MiB and 180 s per file); a file the scan cannot finish is deleted and fails with the kind scan-limit.
  • Document identity. Onshape has no author property to set, so the builder guards instead. At the start of a run, after the leftovers sweep and before the document call, it makes one GET /users/sessioninfo call (counted in the run's calls). The account's name, first name, last name, e-mail and the e-mail's local part (each 3 characters or more and not a generic word) become case-insensitive patterns that match only when no ASCII letter touches them, so ari does not match variable; the values are never logged or printed. If the call fails the run goes on with the OS-user patterns only and run.log says identity patterns: OS user only. The kept-file scan also searches for these patterns (kind account-identity). For every kept STEP file (<id>.step and the bundle's export.step) the FILE_NAME author and organization lists must be empty or exactly Fixture Builder; otherwise the file is deleted and the design fails with kind step-author.
  • Failing closed. A file that cannot be scanned (a read error, a memory error, the limit) is deleted like a hit; when deleting fails the builder retries, then empties the file, then overwrites it in place, and says so in the row. After the designs, on every exit path including a stop on throttle or budget, the builder scans every file under the run folder (a partial bundle after a failed fetch, a file written before an error) and removes a hit. run.log, results.json and trace.json are byte-scanned last; a hit replaces the file with removed by the privacy scan and the console names the file and the pattern kinds. An uncaught error prints error: and the scrubbed traceback, exits 1 and still writes results.json. The user-name rule also refuses a folder whose name only contains your user name (3 characters or more, not a generic word such as Public or admin), such as /Volumes/<name>-ssd/out, and the texts show any user folder under C:\Users, /Users or /home other than Public and Shared as <user folder>.
  • Scan budget. A candidate deflate header inside a file that does not decode to a valid stream (an error, or fewer than 4 bytes of output) is thrown away and does not count against the 256 MiB total; only streams that decode to their end and ZIP members count. Random or compressed data therefore scans to the end without scan-limit, and a real path inside it is still found. Every cap (nesting depth 6, 64 MiB per stream or member, 256 MiB total, 180 s, a ZIP member that cannot be read, a STEP member over 64 MiB, a run folder that cannot be listed) is a hit: the file is deleted and fails with scan-limit or scan-error, never taken as clean.
  • Names in any script. Names, the home folder and the account strings are matched as text against the bytes read as UTF-8, as Latin-1 and as UTF-16LE at both byte alignments, so a Cyrillic or CJK name is found like a Latin one (2 characters or more for a non-ASCII name, 3 for an ASCII name). C:/Users/Public/, Default, All Users and Shared are shared profile folders with either slash; a person's folder there is flagged.
  • STEP header. Every .step, .stp (any letter case) and every STEP member of a bundle gets its whole HEADER section read, up to ENDSEC; and at most 4 MiB; a header that does not end inside 4 MiB fails closed (step-author). The FILE_NAME name field must be a bare file name and the author and organization lists must be empty or Fixture Builder. Before the scan the builder rewrites a kept STEP file (and the STEP member of a bundle, with every other member kept as it was) in place: a name holding / or \ becomes its last component (a full Windows path ending in X.step becomes X.step), the author and organization lists become (''), and every other byte stays the same. The file is then checked again; a header that cannot be rewritten safely (no end, a name that is not one string, a path with no file name) is deleted and the design fails with step-author.
  • Ctrl-C. An interrupt (or any other BaseException) prints interrupted (or a scrubbed traceback), still writes results.json and run.log when the run folder exists, and exits 130 for Ctrl-C.
  • run.log, results.json, trace.json and the console text show your home folder as ~ (%USERPROFILE% for a Windows path) and your user name as a folder name the same way. A path under a user folder is replaced whole: after the head (a user folder under C:\Users, /Users or /home, the home folder, an account folder below, or a network-share path) everything up to the end of the line, a quote (" or '), <, > or | goes, spaces and dots in the last segment included. A user's Dropbox (Acme Corp) folder followed by more text, and a file My Part.x in a user folder, leave no (Acme Corp) and no Part.x. Only the exact folder names Public, Default, All Users and Shared under Users are not a person: Public.ACME and Shared.old are. results.json rows hold no absolute path: a run or output folder in a text reads <run folder> or <output folder>, and output is the run folder name.
  • Machine name. The host name (socket.gethostname()), COMPUTERNAME, USERDOMAIN and LOGONSERVER (leading backslashes removed), each also as its first DNS label, are searched for as whole words (nothing but a non-letter, non-digit, a line start or end, a tab, a quote or a binary length byte next to them) in every form above, UTF-16LE at both alignments and inflated streams included, and a file with a hit is deleted (kind machine-name). Generic names (localhost, WORKGROUP, localdomain and similar) and names shorter than 3 characters (2 for a non-ASCII name) are not searched. Texts show the name as <machine>, and a network-share path as <share>.
  • Profile leaf, OneDrive and Documents. The last component of the home folder counts as a user name even when it differs from the login name (jsmith.ACME), with and without its .DOMAIN suffix. Every OneDrive* environment variable (OneDrive, OneDriveCommercial, OneDriveConsumer), its last folder name, and on Windows the redirected Documents folder (registry key Shell Folders, value Personal; skipped when it cannot be read) are account folders: an output folder inside one, or with that last name as a folder name, is refused before any API call; the full path and the last name are searched for in every file (kind user-folder); and the texts show them as <user folder>.
  • Names as words. The user name and the profile leaf (4 characters or more; 2 for a non-ASCII name), the machine name and the account name are also found alone, not only as a path component: at the start of a file, on a line of their own, after a tab, inside ["..."] and right after a binary length byte, in UTF-8 and in UTF-16LE at both alignments. A letter or digit next to the name means no hit. Texts show a bare user name as ~ or <user folder>.
  • Crash sweep. run() ends in a finally that scans every file under the run folder that no check has cleared (any extension, or none: .tmp, a file without a suffix) and the three text outputs, so a crash in a design, in an export, before the first design or in the end of the run itself (a failing finish_run) leaves no unscanned file. main() runs the same sweep on any crash or interrupt.

Every run writes to a new folder build_onshape-Onshape-<builder version> inside the output folder; if that name exists it takes the first free -2, -3, and so on. Nothing existing is deleted or overwritten. The folder holds results.json, run.log (first line: the full folder path) and trace.json (each added feature and Onshape's regeneration status).

API calls are counted per year on every Onshape plan (2,500 on Free and Standard). The builder counts its own calls, records build_calls on each results.json row, and stops at --max-calls (default 60). A design costs one call to create its Part Studio (none for the first), one per feature, one FeatureScript evaluation before each feature that selects existing geometry (faces, edges, sketch points, bodies), and one measurement.

A revolve about a world axis turns the profile about a construction line that the profile sketch draws on that axis, as a UI user draws a centerline; Onshape has no default axes to select.

Every feature's parameter ids, kinds and enum values are checked by the tests against Onshape's own featurespecs response (builders/tests/onshape_featurespecs.json). The builder posts these features:

  • Offset sketch planes ({base, offset}, or a normal with a non-zero origin) first get an Offset cPlane (cplaneType, entities, offset, oppositeDirection); the sketch frame is read back from the created plane.
  • Sketches: arcs are stored as counter-clockwise circle segments with coincident constraints at shared ends; construction becomes isConstruction, and a revolve or coil reuses a construction line that lies on its axis; a sketch fillet on a rectangle corner is drawn as trimmed lines plus an arc; a projected edge is drawn as the closing line of its chain.
  • extrude: endBound (BLIND, THROUGHALL, UPTO_SURFACE with endBoundEntityFace), symmetric, a second direction (hasSecondDirection, secondDirectionBound, secondDirectionDepth), a start plane (startOffset, startOffsetBound ENTITY, startOffsetEntity), a draft (hasDraft, draftAngle, draftPullDirection; the answer key decides if the sign is right), a symmetric surface extrude for a split tool, and picked sketch regions. revolve is fullRevolve, or fullRevolve false with endBound BLIND and angle, plus oppositeDirection.
  • shell, loft (sheetProfilesArray of sheetProfileEntities), sweep (profiles, path; a 3D path is one planar sketch per line), fillet (also variable: isVariable with a vertexSettings array), chamfer (also OFFSET_ANGLE).
  • Feature patterns and mirrors: linearPattern, circularPattern and mirror with patternType FEATURE and an instanceFunction feature list. A linear direction is a default plane (its normal), a circular axis is the circular edge that lies on the axis, and a mirror plane is a default or offset plane.
  • splitPart (split solid, trim with keepBothSides and keepFront, split face), helix plus sweep for a coil, and assignVariable for a user parameter; #name expressions in a dimension or depth refer to it.
  • Sheet metal: the sketch is extruded to the thickness and converted with sheetMetalStart (CONVERT, thickness, radius, K factor, corner relief rule), then sheetMetalFlange, sheetMetalHem and sheetMetalCornerBreak.

Onshape's offset-and-angle chamfer and its flange name no reference face or direction. The builder measures (the reference face area, the model's bounding box) and deletes and rebuilds the feature flipped when the first try went the other way.

Not scripted, each with its reason in results.json: appearances (not features), a spline sketch entity, a flat spiral coil, the flat pattern (Refold needs the unfolded faces), part-width flanges and bend or corner reliefs that differ from the model's rule, and the assembly rows that need more than instances, transforms and mates (angle and tangent constraints, component patterns, mirrors, model states, view representations, linked or virtual parts, flexible subassemblies, part configurations, and a joint along an axis other than Z).

Assemblies. An assembly design (A01 to A03, A05, A11 to A15, A17 to A19, A25) builds each component part in its own Part Studio, named by the recipe id and built by the same code as a part design (held to the part's answer key), then one Assembly element per assembly. A subassembly is an Assembly element of its own, inserted as an instance. The calls, in order:

  • POST /assemblies/d/{did}/w/{wid} creates the Assembly element; POST .../e/{aeid}/instances inserts each component (isWholePartStudio for a part, isAssembly for a subassembly).
  • POST .../occurrencetransforms places an instance (16 numbers, row-major, meters, isRelative false; an instance at the origin with no turn is not posted); POST .../occurrences sets fixed (the recipe's grounded and ungrounded parts), hidden and suppressed.
  • A mate or flush constraint is a Planar mate, an insert a Revolute mate, between mate connectors (BTMMateConnector-66) on the faces or circular edges the recipe's selectors name, found like the part builder finds them. An offset is the connector's Z translation, a flush is a flipped connector, a suppressed mate is posted with suppressed.
  • A motion recipe (rigid, revolute, cylindrical, planar, ball) is built at its home pose (every degree of freedom at zero): connectors on the two part origins that coincide there, a BTMMate-64 of the matching type with the recipe's limits, then the moving part is moved to the recipe's pose.
  • The assembly is read back (GET .../e/{aeid}) and every instance's placement in the top assembly is compared with the answer key, assemblies in expect.json (translation within 0.001 mm, rotation within 1e-4, grounded and suppressed state). A01 to A10 have no key: the placements the recipe states are compared, and a part a mate moves is not. Degrees of freedom and the assembly bounding box are not read back.

Every Part Studio and Assembly element an assembly design makes goes to leftovers.json (see Cleanup) as soon as it exists, and leaves it when the design succeeds. A design that fails deletes them (DELETE /elements/d/{did}/w/{wid}/e/{eid}): the Assembly elements first, newest first (a subassembly after the assembly that inserts it), then the Part Studios. A throttle or the call budget stops the whole run instead (see Throttling): no delete is made, and the next run deletes the listed elements before any other call, in the same order (Assembly and drawing elements first, newest first, then the Part Studios). The Part Studios built for one assembly design are reused by the later ones of the same run, so a part costs its calls once; only the design that built a Part Studio deletes it when it fails, and a design that only reuses one never does.

Every assembly endpoint, field and mate parameter name is a module constant of builders/gen/onshape_runtime.py marked "sitting": the first assembly sitting confirms them, and a refusal names the fields that were sent. The build's trace.json records every assembly call and answer.

Drawings (D13a to D18a). A drawing companion builds its model (P03a, P03b, P07a, P08a, P06a, P06b) in a Part Studio named <model> for <drawing>, checks it against the model's answer key, then makes the drawing element (POST /drawings/d/{did}/w/{wid}/create: ISO, millimeters, A4, first angle, title block and border, no views). One modify request adds the Front view at 1:1, the Right view (left of it, first angle), the Top view (below it) and the isometric view at 1:2; a second adds section A-A on the Front view through the top and bottom edges at the recipe's x, and a third labels it. Each linear dimension is a point-to-point dimension on the first of Front, Top and Right whose geometry (jsongeometry) holds both points, snapped to an edge end, a circle center or quadrant, or a point on an edge that crosses the dimension. The title block properties Title and Drawn by are set from the recipe. The check exports DRAWING_JSON (views, dimensions, error states, dangling flags, measured values); the files are <id>.pdf, <id>.dxf and <id>.drawing.json, and nothing is stored in the document. Dutchman does not fetch a drawing. A drawing costs 33 to 37 API calls in the mock (the Part Studio, its features, the drawing, four modify requests with one status poll each, the geometry of three views, the title block, three exports); the live cost depends on how long Onshape keeps each request active and is written here after the first drawing sitting. A modify or an export is polled at once, then after 1 s, 2 s, 4 s and so on, at most 15 s apart, for at most 180 s (16 polls), and then fails as "timed out waiting for ...".

Call reserve. Before it starts a drawing, the builder checks that --max-calls minus the calls already made is at least 162, the most one drawing can spend: the 40 calls of the largest drawing in the mock when the views list does not name the views (one extra DRAWINGJSON export), plus 15 further polls for each of its 8 polled requests (120), plus the 2 calls that delete its elements when it fails at the last step. A drawing that does not fit is not started: its row is `notscripted with "call budget left N is below the drawing reserve 162; run it with --max-calls 170 or more". Run a drawing with --only D13a --max-calls 170` or more (the default 60 skips every drawing); a part design never needs the reserve.

Throttling. A 429 answer, or any answer with a Retry-After header, stops the whole run: the row fails with "Onshape throttled <method> <path> (status 429, Retry-After <seconds>); stopping this run", no later design is tried, no cleanup call is made, and results.json, trace.json and run.log are written as usual. The builder never sleeps through a Retry-After (it is often about 23 hours) and never retries.

Cleanup. On success the model Part Studio and the drawing stay in the document: the bundle and the PDF and DXF come from them. When a drawing design fails, the builder deletes the drawing, then its Part Studio (DELETE /elements/d/{did}/w/{wid}/e/{eid}); a failed delete is appended to the row error as "; cleanup: ..." and never replaces the first error. A part design's Part Studio stays in the document when it fails, so the failing features can be looked at. When a throttle or the call budget stops a drawing design, no delete is made; the ids of its elements go to run.log and to leftovers.json, in the output folder that holds the run folders, never to results.json. Each Part Studio and drawing element of a drawing design is added to leftovers.json as soon as it exists and removed when the design succeeds or the element is deleted. At the start of the next run, before any other call, the builder deletes every element listed there (only those of the document it is adding to when --document is given, since the file may name older documents), taking the ids from the file and never by name or listing; an element Onshape no longer has counts as deleted. A throttle during that sweep stops the run and keeps the rest of the file. The file is written to a copy and renamed over the old one.

Field names a live sitting confirms. When the drawing create call or a modify request is refused (a non-200 answer, a FAILED state or an item that is not OK), the row error names what was sent: for create views=zero standard=ISO units=MILLIMETER size=A4 projection=FIRST_ANGLE, for the views, the section and its label (labelDefinition) and the dimensions the field names of that request, and for the title block the property names looked for (Title or Description, Drawn by or Designer) and the names found. The check takes one DRAWINGJSON export per drawing; when the views list does not name the views, the view table reads one earlier, before the section and the dimensions exist, so that case takes two. A drawing whose model is not in the Onshape spec, or not built by it, is `notscripted` ("model P03a not made by the Onshape builder").

Selections are found by geometry, as the recipe selectors state them (a point on the edge or face, and its direction or normal), and are posted as deterministic IDs, the form the Onshape UI stores. A selector that matches zero or several entities fails the design.

ok requires the measured volume and tight bounding box to match the answer key (volume within 0.05 mm³ or 1e-4 relative, bounds within 0.001 mm). failed records an API error, a feature that did not regenerate, or an answer-key mismatch. not_scripted names the operation the builder does not build yet.

With --dutchman <path to dutchman>, each ok design is also fetched with dutchman onshape fetch into <id>.onshape-bundle, and its STEP member is written as <id>.step. A fetch spends its own API calls (recorded as fetch_calls).

Documents built on a personal account show that account's name to anyone who can open them. Keep them private unless the account is one meant for publishing.

Native CAD files carry your Windows user and computer name inside them; we keep native files private and publish only STEP and files we've checked clean.

The recording mock (builders/mock/onshape_com.py) answers the calls the runtime makes. Mock coverage means implemented dispatch, not a real Onshape build. See [coverage](../COVERAGE.md).

Unattended runs. The script only prints the outcome and the next step (and writes them to run.log); it never opens a window, with or without FIXTURE_UNATTENDED=1. Onshape builds in the cloud, so there is no zip: send results.json.
