Run the Fixture Builder in Fusion

Please use a licensed copy.

For volunteers with a current Fusion installation on Windows or macOS. You do not need to write code or install Python separately. The builder makes the supported booklet recipes with real Fusion features and a timeline, then exports local .f3d files and matching STEP copies. Recipes it cannot make are listed with a reason, not silently left out.

Coverage: the Fusion-only recipes (F, M and the Fusion drawings in D) and the common recipes Fusion can make exactly, 144 of the 167 common designs: all 38 part designs (P), 35 of 47 sheet-metal designs (S: the base, edge and contour flanges, hems, corner rounds and flat patterns, through Fusion's sheet-metal rules and flange, hem and flat-pattern calls; the corner round is a plain fillet on the thickness edge, because the sheet-metal fillet is refused on the builder account), 38 of 39 extra-feature designs (X: the coil is a circle swept along a helix wire, because Fusion's API can read coils but not create them), all 16 extent and split designs (E: a trim split is Split Body plus removing the other half, a surface tool is a surface extrude), 15 of 23 assembly designs (A: placing parts, grounding, hiding, suppressing, a component pattern, an appearance override, and mates, flushes and inserts as joints) and 2 of 4 shared part/drawing designs (D). Fusion cannot make the other 23 exactly, so results.json lists each as not_scripted with its reason: the 12 sheet-metal designs without a matching Fusion call or result (S02i has no bend-transition setting, S03f comes out identical to S03a, S08 to S12, S14 and S15b are not mapped yet), the flat spiral coil (X10f), angle and tangent constraints (A04, A06), model states and view representations (A08, A09: configurations are refused on the builder account), and drawings (D05, D07).

Sheet metal: the flange calls (FlangeFeatures.createBaseFlangeInput, createEdgeFlangeInput, createContourFlangeInput and add) are marked as a preview in Fusion 2706.1.17's own API help ("do not use in distributed programs"); they were built and read back on that build, and a Fusion that lacks one makes the recipe fail with the call's own message. The hem, rule, flat-pattern and DXF-export calls are released. The bend position that matches the recipes is Inside (the flange stays inside the plate edge, as in Inventor); the other Fusion builders' "default" is not Fusion's own default (StartEdge).

Assembly recipes A11 to A26: Fusion makes A11 to A22 (placements with turns, the same part twice as true instances, nested subassemblies grounded at every level, rigid, revolute, slider, cylindrical, planar and ball joints with their limits and poses, mirror, linear and circular patterns of a subassembly) and A25 (suppressed components and a suppressed joint). Every joint value, limit and placement is read back, and a recipe fails if Fusion kept a different value (it rejects an out-of-limit value without an error). These are listed not_scripted with their reason: A19c (the ball joint has no cone limit and cannot tilt about Y from a point), A23 (a linked part needs a cloud upload; this account is at its editable-file limit), A24 (no flexible subassembly) and A26 (configurations are refused on this account). Mirror: A20a and A20b use Fusion's Mirror, which makes a new component "(Mirror)"; A20c is a new component built from the mirrored recipe.

Download and run

Save and close your own work first. Each recipe takes a few seconds; the full set takes about 10–30 minutes (10 recipes took about 20 seconds on one test machine; older machines and large sets may take longer). This is an estimate, not a promise. Leave Fusion alone while it runs.

  1. Download FixtureBuilder.zip and unzip it. Keep the extracted FixtureBuilder folder together: it holds FixtureBuilder.py and FixtureBuilder.manifest.
  2. Optional: to build only some recipes, make a plain text file named recipes.txt inside that FixtureBuilder folder, next to FixtureBuilder.py, and type the recipe ids in it, for example P01a M01a (one line, or one per line). No recipes.txt means every recipe. A misspelt id stops the run before anything is built and says which one.
  3. In Fusion, open the Design workspace, then Utilities > Scripts and Add-Ins (shortcut: Shift+S). There is one Scripts and Add-Ins list, not separate tabs. Click +, choose Script or add-in from device in the menu, and pick the FixtureBuilder folder you unzipped (the file chooser opens in Documents, so go to where you unzipped it, for example Downloads).
  4. Click the play triangle in the Run column of the FixtureBuilder row (selecting the row only shows its details). Use it once for the whole batch, not once per recipe. When it finishes, Finder or Explorer opens with the zip selected, and a box says how it went, for example:

> 10 recipes: 9 built, 1 failed, 0 not scripted (details in FixtureBuilder.log). > Next: send this zip to Dutchy in a Discord direct message: > ~/FixtureBuilder/out/FixtureBuilder-Fusion-2026.11.23.1/Fusion-2706.1.17-17.zip

Click OK to close the box.

  1. Open C:\Users\Public\FixtureOut (Windows) or FixtureBuilder/out in your home folder (macOS ~/FixtureBuilder/out). The newest folder there is FixtureBuilder-Fusion-<builder version>, for example FixtureBuilder-Fusion-2026.11.23.1; if a folder for the same version already exists, the builder adds -2, -3 and so on (for example FixtureBuilder-Fusion-2026.11.23.1-2). The finish box gives the exact path. The zip to send is inside it, named for your Fusion build: for Fusion 2706.1.17 that is Fusion-2706.1.17-17.zip.
  2. Send that zip to Dutchy: in Discord, send Dutchy a direct message with the zip attached (or post it in your volunteer thread). Say you used the Fusion Fixture Builder and give your Fusion build. Dutchy reads the builder version, your Fusion build and every recipe's result from the zip, and replies with a receipt.

This route needs nothing but Fusion and the unzipped folder. Downloads come from fixtures.dutchmancad.xyz/builders/.

Our own test machines also run the same builder through a private queue add-in as fixture_job.py (download fixture_job.py; there RECIPE_FILTER = ['P01a', 'M01a'] picks recipes). You do not need it.

What happens on your machine

The builder picks its own output folder: every run makes a brand-new folder named FixtureBuilder-Fusion-<builder version> (for the queue job, fixture_job-Fusion-<builder version>); if that name is already taken it uses -2, -3 and so on, so an earlier batch is never reused, emptied or overwritten. You do not create or choose that folder; only the parent location can be chosen. The builder opens documents to make the fixtures, exports them locally, and closes the documents it created. It writes .f3d files, .step copies, results.json, FixtureBuilder.log, a run.log and one zip named for the Fusion version and build, all inside that new folder.

The zip holds the designs, the STEP copies, results.json and FixtureBuilder.log. FixtureBuilder.log says which builder version made the run and has one line per recipe; it holds no folder paths or names. run.log stays on your computer: its first line is the full output folder path, so it is never put in the zip.

Open results.json in a text editor when it finishes. ok means that recipe was exported; failed includes the app's error; not_scripted explains what still needs making by hand or another API feature. Partial batches help too. A saved file still needs the portal's checks.

Manufacture recipes (M01 to M11)

The M recipes (a plate and a dome, a setup with a stock box and work coordinate system, a three-tool set, and one operation per recipe) need Fusion's Manufacture workspace. For each one the builder builds the part, switches to Manufacture, makes the setup and the operations, generates every toolpath, then switches back to your workspace and exports the design. It makes its three tools from its own definitions and never reads, imports or changes your tool library. A recipe is ok only when every toolpath generated and every value it set reads back as the recipe says, and each work coordinate origin is where the recipe says; otherwise it is failed with the reason. M02a also writes M02a.tools, and M11a and M11b write the posted program (M11a__fanuc.nc, M11b__haas.nc) with the post processor that ships inside the Fusion application folder.

Privacy and sending the zip

The builder exports new, unsaved designs locally instead of saving them to a Fusion cloud project. It leaves author/company fields blank where available and clears editable descriptions and STEP author details. It does not collect your account name. The builder waits a moment before each export so that Fusion's default material asset is written without your Fusion account id, and its NC program uses a copy of the post processor and a work folder outside your home folder. One exception: the M recipes' designs still carry Fusion's own toolpath message log, which names Fusion's install folder (a path under your home folder, so with your operating-system account name); the API has no way to clear it. Some assembly designs can also hold a library path under the install folder in their graphics scene, which the builder cannot prevent either. The portal's own privacy scan still runs; blank properties do not replace that scan. Files stay private unless you choose CC0 when uploading.

Native CAD files (.f3d…) carry your Windows user and computer name inside them; we keep native files private and publish only STEP and files we've checked clean.

Send the zip to Dutchy as step 6 above says, or, if you prefer, upload it yourself from your private link: curl -F bundle=@FIXTUREZIP -F consent=private https://fixtures.dutchmancad.xyz/v/YOUR-PRIVATE-TOKEN/builder (the zip in the bundle field; consent is private, the default, or cc0). It answers with a JSON receipt listing the batch, the counts and each recipe's upload, the same records Dutchy's receipt is made from. Keep the link private. Files stay private unless you tell us you want them public (CC0). Read the receipt and any rejected-file reasons. The portal's own bulk upload address is only for CAM design files and does not take a builder zip. The receipt lists your recipes. Every built recipe the portal's Fusion list asks for (F, the common P, X, E, S and A, D and M) becomes an upload row. A built recipe the list has no step for (one the booklet marks for another app only) is kept with your batch's files; the receipt says so in plain words and nothing is lost.

If Discord is not an option, upload the zip to Google Drive or Dropbox and send the sharing link to Dutchy in a DM, with the same build and builder note. Keep your portal link private. Do not describe a scripted batch as made by hand or agree to a statement that does not describe your run.

Unattended runs. For the queue job (fixture_job.py), or when FIXTURE_UNATTENDED=1 is set, no message box opens and Finder or Explorer is not touched; the same message goes to Fusion's text log and run.log.

Privacy: the builder writes your home folder, and everything below it, as %USERPROFILE%\<path> (Windows) or ~/<path> in every log and JSON file inside the zip (a path in a network-share form (backslashes, forward slashes or smb://) likewise; a path ends at the end of its line or at a quote, so a sentence after a path on the same line can be lost), sets the name properties of a saved document (CreatedBy, LastModifiedBy, Company, Author and so on) to "Fixture Builder", scrubs any text in the .f3d, gives the STEP header the bare file name and "Fixture Builder" as author and organization, and then scans every file in the run folder (also inside the zips and compressed streams) for your user folder path, your user name, your profile folder name, your computer name and OneDrive, as ASCII, UTF-8 and UTF-16. The scan looks for UTF-8 and UTF-16 only: both builders write UTF-8, and legacy ANSI code pages are not searched. A file that still has a hit, cannot be checked, or is too big to check in time (a binary part over 64 MB) is not kept: its row says "a file still contains your user folder path; it was not kept", and the run goes on. An output folder whose path has your user name, profile folder name or OneDrive is refused before anything is built. An account display name such as "John Smith" is removed only from the document properties named above and from paths, not from anywhere else in a file. Fusion's own archives compress some parts with zstd; a Python older than 3.14 cannot open those parts, so those parts are not scrubbed and are checked only in their packed form, and the row says so. The parts it can read are still scrubbed.
